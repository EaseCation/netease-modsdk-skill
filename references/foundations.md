# 工程结构与职责

用于新建或重构普通 Addon。先识别项目既有约定；以下分层是建议，不要求为小组件建立框架。

## 从加载链确定文件

```text
BP/manifest.json                    RP/manifest.json
BP/entities/                        RP/textures/
BP/<团队模组>Scripts/
  __init__.py
  modMain.py                        绑定入口、注册双端 System
  server/                           权威状态、规则、持久化、引擎调用
  client/                           输入、UI、模型与粒子表现
  common/                           常量、事件结构、无端侧依赖的计算
```

1. 核对 BP/RP 的 UUID、依赖和版本；命名空间、纹理简称及脚本根包名避免与其他组件冲突。`format_version` 是该文件的格式，不统一替换为目标游戏版本。
2. `modMain.py` 位于脚本包内，包目录保留 `__init__.py`。用 `Mod.Binding` 绑定入口，在 `InitServer/InitClient` 中注册对应 System。纯资源组件不为凑结构添加 Python。
3. System 管监听、生命周期和引擎边界；复杂规则可提取为领域模块，UI 类只管理视图与交互。客户端与服务端不互相 import；`common` 也不能间接导入端侧模块。
4. 引擎组件是通过组件工厂获得能力的入口；JSON `components` 是资源/行为声明；项目业务模块是代码组织。三者同名概念不能互相替换。调用前核对组件绑定的是实体 ID、玩家 ID 还是 levelId。
5. 客户端发送操作意图；服务端核对身份、目标、距离、数量和当前状态后执行，再通知有需要的客户端。字段名、单位和消息版本集中定义。不要直接把客户端传来的结果作为权威数据。
6. 注册与销毁成对管理：监听、定时器、UI、粒子句柄和实体引用。玩家退出、切维度、区块重载各自有生命周期，不能只等整个 Mod 销毁。

Python 语法按目标 ModSDK 的解释器核验；现有教程以 Python 2.7 为基础，不能把本工具运行所需的 Python 3 当成游戏解释器。保持工程已有风格；用明确的单位和端侧命名，避免跨模块循环依赖、隐式全局状态、每帧全量扫描和巨型 System。性能优化以实际频率与对象数量为依据。

## 路线对比

| 能力 | 中国版普通 Addon | 国际版数据包 | 边界 |
| --- | --- | --- | --- |
| BP/RP、manifest、标识符与资源引用 | 支持，另有网易专用目录 | 共享总体组织 | 文件名相似不证明字段合同相同 |
| 逻辑入口 | `*Scripts/modMain.py` 与双端 System | JSON 组件、实体事件、函数等数据驱动入口 | 网易 Python 类不能直接移植 |
| 内容声明 | 原版机制及 `netease_*` 扩展 | 对应版本的标准目录与组件 | 按模块选路线，不混合两套注册格式 |
| 运行状态 | 服务端规则，客户端表现，通过消息协作 | BP 行为与 RP 表现职责分离 | RP/Molang 变量不等于服务端持久化数据 |

只有需要 API 合同时转 [API 查询](api-query.md)：拆成注册系统、监听/取消监听、通知指定玩家、延迟执行、持久化等职责，不用整段架构说明搜一次。
